# 3. Functional Requirements & Acceptance Criteria

The functional requirements below are derived directly from the stakeholder needs identified in Section 2. Each requirement has a unique identifier, an explicit source stakeholder, an indicative priority, and a testable acceptance criterion, in line with the Master Project Brief's requirements standard (Section 11).

| ID | Functional Requirement | Source | Priority | Acceptance Criterion |
|---|---|---|---|---|
| **FR-001** | The system shall allow requesters to submit a new service request with the required information. | Requester | High | A requester can submit a request and the system creates a unique request record. |
| **FR-002** | The system shall allow requesters to view the current status of their submitted requests. | Requester | High | A requester can select a submitted request and see its current, controlled status. |
| **FR-003** | The system shall allow authorised staff to view service requests relevant to them. | Staff | High | An authorised staff member can access their relevant requests after logging in. |
| **FR-004** | The system shall allow authorised staff to assign or accept responsibility for a request. | Staff | High | A staff member can assign/accept a request and the responsible person is recorded. |
| **FR-005** | The system shall allow authorised staff to update the status of a request through controlled status transitions. | Staff | High | A permitted status change updates the request and records the new status and timestamp. |
| **FR-006** | The system shall allow staff to record comments, actions or resolution information against a request. | Staff | Medium | A staff member can add information to a request and it is saved against that request, retaining its author and time. |
| **FR-007** | The system shall allow management to identify open, overdue, resolved and closed requests. | Management | Medium | Management can view requests filtered or grouped by these statuses. |

Priority reflects the requirement's contribution to the core problem (visibility, accountability and traceability) and is a draft assignment for team confirmation ahead of baseline sign-off; it is not yet linked to a formal MoSCoW or numeric scoring exercise.
